## 影响使用的问题

### 1. 大图草稿恢复后缺少图片正文

位置：`apps/desktop/src/lib/draftPersistence.ts:67`、`apps/desktop/src/state/durableState.ts:17`

草稿 JSON 超过 1,500,000 字符时，持久化逻辑会退化为仅存附件元数据。图片附件通常需要 Base64，大图很容易触发该预算。重启恢复后附件记录仍在，但图片数据已缺失，发送内容构造又只发送带 `data` 的图片，因此可能只发送文字

复现：构造一张带 2,000,000 字符数据的图片附件，执行保存和恢复，恢复结果保留文件名但 `data` 为 `undefined`。已用现有草稿保存与恢复函数复现

建议：图片草稿先保存到本地文件，草稿记录引用路径。无法保留内容时明确提示附件需要重新选择，并阻止把缺少数据的附件当作已发送

### 2. 等待队列只按文字判断重复

位置：`apps/desktop/src/state/store.ts:3121`

同一句「看这张图」附两组不同图片，第一条已经排队时，第二条会被判断为重复并返回 `false`。附件差异没有参与判断，妨碍连续处理多张照片

复现：运行中的会话已有一条文字相同、图片不同的队列记录，再执行实际 `sendPrompt`，返回 `false` 且队列仍只有原记录

建议：依照用户提交标识或附件身份判断重复，保留同文字、不同图片的独立提交

### 3. Git 推送固定使用 origin 并改写上游跟踪关系

位置：`apps/desktop/src-tauri/src/main.rs` 的 `prepare_git_push`、`git_push`

确认窗口固定写 `origin`，执行使用 `git push --set-upstream origin <当前分支>`。具有多个远端、当前分支跟踪其他远端时，界面不能沿用已有上游，还会在推送后改变跟踪关系。本轮已按授权把 Grox 自身的 `origin` 改为自有仓库，消除了本项目继续指向原作者的直接风险，该通用行为仍待修复

证据：源码命令及本轮修改前实际配置，当前分支原本跟踪 `my/main`，而 `origin` 指向原作者。未向原作者仓库执行推送

建议：确认窗口展示实际远端和目标分支，令牌绑定该目标，优先使用已设置的上游。没有上游时再要求选择，执行时再次核对目标

### 4. SVG 路径被自动识别为图片，但后端拒绝

位置：`apps/desktop/src/lib/pathAttachments.ts:13`、`apps/desktop/src-tauri/src/main.rs` 的 `checked_explicit_prompt_image`

前端图片路径规则包含 SVG，后端只接受 PNG、JPEG、GIF、WebP、BMP。因此在普通指令里引用已有 SVG 文件，会进入自动附件准备，然后因格式不支持而阻止发送

证据：已复现 `imagePathsInText` 将 `assets/vector.svg` 纳入附件候选，并核对后端的实际格式校验。未执行真实模型请求

建议：统一前后端支持列表。SVG 可保留为文件路径上下文，或经明确的转换流程生成视觉预览

## 需进一步验证的稳定性风险

`apps/desktop/src-tauri/src/runtime_lifecycle.rs:475` 使用按行读取接收 CLI 输出，入站没有与出站相对应的消息字节预算。若第三方工具生成特别大的单行图片事件，仍可能产生较高内存和界面延迟。已确认源码没有该处的长度限制，尚未测量真实运行内存或复现崩溃，因此不将其列为已发生的故障
